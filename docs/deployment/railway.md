# Railway Deployment Runbook

This project is set up to deploy to Railway with:

- one Railway project
- two Railway environments: `staging` and `production`
- one Postgres service named `postgres`
- one public API service named `api`

The `api` service deploys from this repository's `Dockerfile` and `railway.toml`.
During every Railway deploy, Railway runs:

```bash
alembic upgrade head
python scripts/bootstrap_admin.py
```

That pre-deploy step keeps the schema current and ensures the treasury wallet is
an admin account.

## What Gets Created Automatically

- The Railway deploy uses `/health/ready` as the service health check.
- `scripts/bootstrap_admin.py` derives the wallet address from
  `APP_TREASURY_PRIVATE_KEY`.
- If an account already exists for that wallet, it is promoted to `is_admin=true`.
- If no account exists, the script creates one with:
  - `display_name="Treasury Admin"`
  - `account_type="human"`
  - `is_admin=true`

After the treasury wallet signs in through the normal SIWE flow, it can use the
admin routes.

## Before You Start

You need:

- a Railway account
- a GitHub repository that contains this code
- permission to create GitHub Actions environments and secrets
- a Base Sepolia RPC URL
- a Base Sepolia treasury private key
- a JWT secret for the API
- a public hostname for each environment
- CDP x402 credentials if you are using the CDP facilitator

## 1. Clone And Prepare The Repository

```bash
git clone <repo-url>
cd agent-marketplace
uv sync
```

The deployment flow uses:

- [railway.toml](../../railway.toml)
- [Dockerfile](../../Dockerfile)
- [scripts/bootstrap_admin.py](../../scripts/bootstrap_admin.py)
- [.github/workflows/release.yml](../../.github/workflows/release.yml)

## 2. Create The Railway Project And Environments

In Railway:

1. Create one project for this backend.
2. Create two environments named `staging` and `production`.
3. Keep the environment names exactly as `staging` and `production` because the
   release workflow deploys to those names directly.

## 3. Create The `postgres` Service

In the same Railway project:

1. Add a PostgreSQL service.
2. Rename the service to `postgres`.
3. Let Railway finish provisioning it.
4. Copy or reference the private connection string from that service for
   `APP_DATABASE_URL` in each environment.

Use the internal connection string generated by Railway for the `postgres`
service. Do not use a localhost URL.

## 4. Create The `api` Service

In the same Railway project:

1. Add a new service from this GitHub repository.
2. Rename the service to `api`.
3. Use the repository `Dockerfile` and `railway.toml`.
4. Attach a public domain to the `api` service in each environment.
5. Confirm the service health check path is `/health/ready`.

`railway.toml` is already configured so the service deploy uses:

- Dockerfile builds
- `/health/ready` health checks
- pre-deploy migration and admin bootstrap

## 5. Configure Railway App Variables

Set these variables on the `api` service for each Railway environment before the
first deploy.

### Variables Required In `staging`

- `APP_ENV=staging`
- `APP_DEBUG=false`
- `APP_DATABASE_URL=<private postgres connection string>`
- `APP_JWT_SECRET_KEY=<strong random secret>`
- `APP_SIWE_DOMAIN=<staging hostname only, no scheme>`
- `APP_PAYOUTS_ENABLED=true`
- `APP_PAYOUTS_RPC_URL=<Base Sepolia RPC URL>`
- `APP_PAYOUTS_CHAIN_ID=84532`
- `APP_TREASURY_PRIVATE_KEY=<Base Sepolia treasury private key>`
- `APP_X402_FACILITATOR_URL=https://api.cdp.coinbase.com/platform/v2/x402`
- `APP_X402_NETWORK=base-sepolia`
- `APP_X402_NETWORK_CAIP2=eip155:84532`

### Variables Required In `production`

- `APP_ENV=prod`
- `APP_DEBUG=false`
- `APP_DATABASE_URL=<private postgres connection string>`
- `APP_JWT_SECRET_KEY=<strong random secret>`
- `APP_SIWE_DOMAIN=<production hostname only, no scheme>`
- `APP_PAYOUTS_ENABLED=true`
- `APP_PAYOUTS_RPC_URL=<Base Sepolia RPC URL>`
- `APP_PAYOUTS_CHAIN_ID=84532`
- `APP_TREASURY_PRIVATE_KEY=<Base Sepolia treasury private key>`
- `APP_X402_FACILITATOR_URL=https://api.cdp.coinbase.com/platform/v2/x402`
- `APP_X402_NETWORK=base-sepolia`
- `APP_X402_NETWORK_CAIP2=eip155:84532`

### Conditionally Required Variables

Set these in any environment where `APP_X402_FACILITATOR_URL` points at the CDP
facilitator:

- `APP_X402_CDP_API_KEY_ID=<CDP API key id>`
- `APP_X402_CDP_API_KEY_SECRET=<CDP API key secret>`

If you change `APP_X402_FACILITATOR_URL` away from the CDP facilitator, keep it
consistent with your chosen facilitator and only set the CDP credential
variables when that facilitator actually requires them.

## 6. Configure GitHub Environments And Secrets

Create two GitHub Actions environments in the repository:

- `staging`
- `production`

Add these secrets to each GitHub environment:

- `RAILWAY_TOKEN`
- `RAILWAY_PROJECT_ID`

`RAILWAY_TOKEN` should be a Railway token that is allowed to deploy the target
environment. `RAILWAY_PROJECT_ID` should be the Railway project id for this
backend. If both GitHub environments deploy to the same Railway project, the
project id will usually be the same in both environments.

## 7. Run The Release Workflow

From GitHub Actions, run the `Release` workflow manually.

Use these inputs:

- `target_environment=staging` and `smoke_base_url=https://<staging-domain>` for
  the staging deploy
- `target_environment=production` and
  `smoke_base_url=https://<production-domain>` for the production deploy

The workflow will:

1. upload the repository to Railway with `railway up --ci`
2. let Railway build the image from the `Dockerfile`
3. let Railway run the pre-deploy migration and admin bootstrap
4. run deployment smoke checks against:
   - `/health/live`
   - `/health/ready`
   - `/v1/auth/nonce`
   - `/v1/services`

## 8. Verify The Admin Bootstrap

After the first successful deploy:

1. sign in with the treasury wallet through the normal wallet auth flow
2. confirm the account can access admin routes

If you need to run the admin bootstrap locally against a target database, use:

```bash
make bootstrap-admin
```

That command reads `APP_DATABASE_URL` and `APP_TREASURY_PRIVATE_KEY` from the
current environment and applies the same admin bootstrap logic used in Railway
pre-deploy.

## 9. What To Check If Deployment Fails

- The `api` service must be named exactly `api`.
- The Postgres service must be named exactly `postgres`.
- `APP_ENV` must be `staging` in staging and `prod` in production.
- `APP_PAYOUTS_ENABLED` must be `true` in both deployed environments.
- `APP_DATABASE_URL` must point to the Railway Postgres service, not localhost.
- `APP_SIWE_DOMAIN` must be the hostname only.
- `APP_PAYOUTS_RPC_URL` and `APP_TREASURY_PRIVATE_KEY` must both be set.
- If using the CDP facilitator, both CDP credential variables must be set.
- `smoke_base_url` must match the public domain attached to the `api` service.

## Later: Add Redis

Redis is intentionally not required for the first Railway deployment.

When you add Redis later:

1. create a Railway Redis service named `redis`
2. expose its Railway-generated connection string to the `api` service
3. add the future app Redis env var from that `REDIS_URL`

This repository does not depend on Redis yet, so do not add it as a required
service in the initial deployment.
